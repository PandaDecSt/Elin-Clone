## 查证：Elin 渲染层是否有 obj 堆叠高度算法（源码，未改 H5）

- **结论：Elin 渲染层也没有按同格堆叠层数垂直抬高的算法。** 证据链：
  - `RenderDataObj.Draw`：`p.z + _offset.z` 即世界 z；`p.z` 来自 `RenderRow.GetRenderParam`→`point.Position(bridgeHeight)`（地形高度），`_offset.z` 来自 `SetRenderData` 里 `pmesh.size/pos` 的 sprite 居中偏移。两者都**无堆叠层数项**。

  - `Scene.cs`/`Zone.cs` grep 不到任何 deco 堆叠抬高渲染调用。
- 含义：Elin 地图上同格多 obj/deco 是平铺在地形高度 + 靠 stackOrder 决定遮挡，**不做垂直空间堆叠偏移**。H5 若想做堆叠表现，需自行按运行时 deco 堆叠数算每层层高偏移（源表/源码均无现成值）。本轮仅调研，未改 iso.js/game.js/materials.js。

## 查证：Elin 建设系统"房子高度"如何实现（源码，未改 H5）
- 用户追问"房子的高度怎么实现的"。与 deco 堆叠是两回事——房子高度是**格子级 `bridgeHeight` 字段**，不是 obj 堆叠。核心源码：`Elin/Point.cs`、`Elin/Map.cs`、`Elin/TileTypeBridge.cs`、`Elin/RenderRow.cs`(GetRenderParam/Position 透传)。
- **存储**：每个地图格子 `cell` 有 `height`(地形) 与 `bridgeHeight`(桥/地台/楼层) 两个 byte 字段。
- **高度渲染公式**（`Point.Position()`，`Point.cs:565-572`）：`b = (cell.bridgeHeight==0 ? cell.height : cell.bridgeHeight)`；世界 `y = (z-x)*tileAlign.y + b * tileMap._heightMod.y`；`z = 1000 + ... + b*_heightMod.z`。即**等距斜投影 + 每格高度 b 控制的世界 y/z 偏移**。
- **建设系统写入**（`Map.SetBridge`，`Map.cs:994-997`）：`cell.bridgeHeight = (byte)height;`。玩家铺桥/地板时传 height，受 `TileTypeBridge.MaxAltitude`（普通 15 / 按住 Shift 30）限制——这就是房子能盖几层的高度上限。
- **物件自动抬高**：墙/家具/地板渲染都经 `GetRenderParam(point, bridgeHeight)`→`point.Position(bridgeHeight)`（bridgeHeight 默认 -1 时自动用 `cell.bridgeHeight`），因此放在 height=N 的地板格上的墙/家具/obj 自动获得该 y 高度。墙比地板"高"是因为 wall block sprite 自身 pmesh 高度，且都站在同一 bridgeHeight 上；多层楼=地板格 bridgeHeight 设更高值。
- **与 deco 堆叠对比**：deco 同格多物件是平铺 + stackOrder 排序（无垂直偏移）；房子高度是格子 bridgeHeight 机制，物件放上去即整体抬高。两者无关。
- 落档 `data/elin_source/Point.cs`(高度核心)、`TileTypeBridge.cs`。本轮仅调研，未改 H5。

## 程序化着色：H5 vs Elin 源码差异 + 补齐非树木 obj 上色（已改，已验证）

- **`THRESH` 24→8（灰度范围收窄）**：实测 objs.png 通道差直方图，白桦(56)叶(cd<8)与干(cd 8~12)正好以 8 为断崖（[4,8)=13.4% / [8,12)=28.9%），THRESH=8 完美分隔→叶染色/干保留灰白(白桦白皮)；橡树 97.6% cd<8、樱/苹果彩色像素 cd>16 均不受影响。

## 墙体双向自动衔接补角（已实现并验证 PASS）
- **用户需求**："给两个方向的自动衔接补角，就是多加一块" —— 放置墙时若与邻居墙方向不同，自动在当前格补一块相反方向的墙，使两个方向的墙能平滑衔接成拐角。

## 修复墙体四边闭环渲染（最终版：dx=0 居中 + 翻转改为 sw/nw）
