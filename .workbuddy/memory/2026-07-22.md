## 查证：Elin 渲染层是否有 obj 堆叠高度算法（源码，未改 H5）

- **结论：Elin 渲染层也没有按同格堆叠层数垂直抬高的算法。** 证据链：
  - `RenderDataObj.Draw`：`p.z + _offset.z` 即世界 z；`p.z` 来自 `RenderRow.GetRenderParam`→`point.Position(bridgeHeight)`（地形高度），`_offset.z` 来自 `SetRenderData` 里 `pmesh.size/pos` 的 sprite 居中偏移。两者都**无堆叠层数项**。

  - `Scene.cs`/`Zone.cs` grep 不到任何 deco 堆叠抬高渲染调用。
- 含义：Elin 地图上同格多 obj/deco 是平铺在地形高度 + 靠 stackOrder 决定遮挡，**不做垂直空间堆叠偏移**。H5 若想做堆叠表现，需自行按运行时 deco 堆叠数算每层层高偏移（源表/源码均无现成值）。本轮仅调研，未改 iso.js/game.js/materials.js。

## 查证：Elin 建设系统"房子高度"如何实现（源码，未改 H5）
- 用户追问"房子的高度怎么实现的"。与 deco 堆叠是两回事——房子高度是**格子级 `bridgeHeight` 字段**，不是 obj 堆叠。核心源码：`Elin/Point.cs`、`Elin/Map.cs`、`Elin/TileTypeBridge.cs`、`Elin/RenderRow.cs`(GetRenderParam/Position 透传)。
- **存储**：每个地图格子 `cell` 有 `height`(地形) 与 `bridgeHeight`(桥/地台/楼层) 两个 byte 字段。
- **高度渲染公式**（`Point.Position()`，`Point.cs:565-572`）：`b = (cell.bridgeHeight==0 ? cell.height : cell.bridgeHeight)`；世界 `y = (z-x)*tileAlign.y + b * tileMap._heightMod.y`；`z = 1000 + ... + b*_heightMod.z`。即**等距斜投影 + 每格高度 b 控制的世界 y/z 偏移**。
- **建设系统写入**（`Map.SetBridge`，`Map.cs:994-997`）：`cell.bridgeHeight = (byte)height;`。玩家铺桥/地板时传 height，受 `TileTypeBridge.MaxAltitude`（普通 15 / 按住 Shift 30）限制——这就是房子能盖几层的高度上限。
- **物件自动抬高**：墙/家具/地板渲染都经 `GetRenderParam(point, bridgeHeight)`→`point.Position(bridgeHeight)`（bridgeHeight 默认 -1 时自动用 `cell.bridgeHeight`），因此放在 height=N 的地板格上的墙/家具/obj 自动获得该 y 高度。墙比地板"高"是因为 wall block sprite 自身 pmesh 高度，且都站在同一 bridgeHeight 上；多层楼=地板格 bridgeHeight 设更高值。
- **与 deco 堆叠对比**：deco 同格多物件是平铺 + stackOrder 排序（无垂直偏移）；房子高度是格子 bridgeHeight 机制，物件放上去即整体抬高。两者无关。
- 落档 `data/elin_source/Point.cs`(高度核心)、`TileTypeBridge.cs`。本轮仅调研，未改 H5。

## 程序化着色：H5 vs Elin 源码差异 + 补齐非树木 obj 上色（已改，已验证）

## 树干/树叶选择性着色（用户追问"树干有颜色、只染树叶"，已改，已验证）
- 用户指出：部分树"树干本来就有颜色，只是树叶需要上色"，直接整张乘色会把树干也染了。
- **Elin 源码真相**（BaseTileMap.cs:3166-3172 + RenderDataObj.Draw:25）：obj 只乘**一个** `matColor`（`colorMod==0`→`104025`=白不染），**整张精灵统一着色，没有任何"只染树叶"的代码路径**。树干/树叶的颜色差异**完全来自贴图美术本身**（树精灵在 objs.png 里就已画好棕干+绿叶，`colorMod=0` 不乘色）。即 Elin 靠 `colorMod` 门控 + 贴图预着色，而非运行时分区域。
- **我们的真问题**：`objs.png` 导出不一致，把部分树做成了"树干已着色 + 树叶变灰遮罩"的**混合精灵**（实测：118 feywood / 119 coralwood / 17 palulu / 63 fossil 等 `trunkChDiff≈74-177` 而 `leafChDiff≈0-5`），而 Elin 里这些本该整张预着色。纯灰树(56/57/58/54/55/70)、全预着色树(76 willow/53 rosewood/49-114 果树)、全着色蘑菇树(12/15/47) 也并存 —— objs.png 是三种状态混合。
- **修复方案 = 渲染端"选择性着色"原语**（不依赖重导出贴图，直接解决混合精灵）：在 `iso.js _getTintedTile` 的 `'colorize'` 模式里**自动判定**精灵像素：
  - 纯灰遮罩(无通道差>24 的像素) → 整张按亮度着色（落叶/花/纯灰树，旧行为）；
  - 含已着色像素(树干/花) → **只染中性(灰白)像素=树叶**，保留已着色像素=树干；
  - 全已着色(无中性像素) → 不着色，直接返回原图。
  - 阈值 `THRESH=24`（树干通道差 42-177 与树叶 0-5 之间有干净分界）。
- **补叶色**：`build_materials.py OBJ_TINT` 增补之前漏掉的混合树 `17/54/55/58/112/118/119/13` 的叶色(RGB)，并 re-enable 樱 77(`[230,150,185]`)。`drawDecoration` 仍走 `def.tint || (def.colorMod && tintForMat)` 门控，新树有了 `def.tint` 即触发 colorize。
- **验证**：node --check 通过；`verify_runtime.mjs` 0 page/runtime error、0 bad request（仅 favicon 404）；PIL 复现选择性算法确认 **trunk 保真误差=0.00（完全保留）**、树叶染成目标叶色（受亮度缩放产生明暗，符合预期）。
- **已知限制（向用户说明）**：① 灰度遮罩树(56/57/58 等)被染成单色(叶色)符合 Elin 单色树风格，但树干与叶同色(无棕干)——因导出丢了树干预着色，重导出 objs.png 忠实保留棕干才是完全还原；② 混合树的叶色是手写近似(非 Elin 真实叶色)，重导出贴图 + `colorMod=0` 才是真源；③ 阈值 24 对极少数"白高光预着色树"可能略染高光，属可忽略。

## 着色算法修正：灰遮罩树改 multiply 保纹理（用户反馈"只有柳橡对"）
- **根因**：上一轮的 `'colorize'` 模式把纯灰遮罩精灵整张替换成 `tint * brightness_factor` 平板色——**丢了所有纹理细节**（树皮纹路、叶脉、明暗阴影）。对比预着色树(apple/mahogany/orange)的丰富细节，灰遮罩树变成"平板绿块"。
- **用户反馈**："好像就柳树和橡树是对的"——说明 oak(58)/willow(76) 的观感可接受，其余全不对。
- **实测精灵分类（alpha 通道精确版，全部 147 obj）**：用 PIL RGBA 逐像素通道差分类：
  - `PRE-COLORED(full)` (fracCol>0.5)：0 momiji/2 blue flower/13 christmas/16 cactus/19 gem/35 wheat~42 crops/49 apple/69 mahogany/77 cherry/78 grape/79 leaves/88 rice/90 rainbow/91 salt/99 cattail/102 sulfur/104 api/108 silver/112 banana/113 orange/114 pear/119 coralwood/121 fern/122 coffee/123 tobacco/136 coral reef/137 seaweed/138 cabocchi/139 sunflower/140 tulip/141 pepper/144 stepping stone 等 ≈60 个
  - `MIXED(trunk+grayleaf)` (0.05<fracCol≤0.5)：17 palulu/28-30 roof/29 roof5/31 track/33 stone road/43 road/53 rosewood/62 fossil-decay/63 fossil/74 shell/81 cotton/82 remain/84 mound/85 wreck/86 wreck/92 border/94 decayed tree/103 bamboo/105 pasture/109 debris/124-125 roof/129 roof12/131-134 roof/142 bone mound 等
  - `GRAY-MASK` (fracCol≤0.05)：9 pebble/11 stone/25 road/32 chasm/34 wreck/44 narrow/51 rock/55 cedar/56 birch/57 pine/58 oak/59 burnt/66 bollard/70 acacia/72 stump/76 willow/93 stalagmite/95-96 decayed wall/97 track/100 huge rock/110 conveyor/126-128/132-133 roof 等
  - `empty`(非透明<20px)：1 flower/3 yellow flower/4 white flower/5 weed/6 mushroom/7 weed/8 rafflesia/12 mushroom tree/14 crim/15 mushroom tree/18 ore/24 frame/45 chunk/47 mushroom tree/48 nest/50 berry/52 bone/54 fir tree/60 moss/61 vine/65 decayed fossil/71 cracked/73 seaweed/75 coral/80 test/71 crack/89 line/106 metal/107 chems/111 frag/115 red grass/116 blue/117 purple/118 feywood/120 white flower/127 green grass/135 neon/145 egg 等 → **rect 错位或精灵本身极小**
- **核心修复**：`iso.js _getTintedTile colorize` 分支中，`!hasColored`（纯灰遮罩）从 pixel-by-pixel **colorize（平板色）改为 canvas **multiply（保纹理）**：`drawImage→globalCompositeOperation='multiply'→fillRect(tint RGB)→source-over`。multiply 对 R≈G≈B 的灰度遮罩效果 = 保留全部纹理（树皮/叶脉/阴影），仅做颜色偏移。MIXED 分支保持选择性 colorize 不变。PRE-COLORED 返回 null。
- **补缺失 tint**：OBJ_TINT 新增 `53 rosewood[145,180,100]` / `59 burnt[65,50,38]` / `72 stump[115,85,50]` / `105 pasture[118,168,88]`。
- **验证**：node --check 通过；verify_runtime.mjs 0 error；PIL 复现 v2 对比图确认灰遮罩树(oak/birch/pine/cedar/acacia) 全部保留纹理细节、混合树(palulu/rosewood) 树干保留+叶绿。
- **遗留问题**：① **大量 obj rect 为 empty**（12/15/47/54/76/118 willow/feywood 等 ~30 个）→ 这些精灵在 objs.png 中读到了透明区域，**obj_id_rect 坐标错位需修复**；② 柳树(76) rect 也在此列（用户说"柳树对"可能实际看到的是 fallback 或别的 id）。
- **修复 `_getTintedTile` colorize 分支 ReferenceError: inv is not defined**（iso.js:601）：上一轮拆分 `!hasColored`/`nNeutral>0` 分支时，把 `maxL`/`inv` 计算留在了被删的旧 colorize 块里，导致混合精灵分支用 `inv` 未定义。修复：分类循环里累计 `maxL`，在 `nNeutral>0` 分支开头 `const inv = 255 / maxL;`。verify_runtime.mjs 复测 0 page error（仅 favicon 404）。
- **修复 透明背景被填成纯色块**：`!hasColored`（纯灰遮罩→multiply）分支只做了 `multiply fillRect` 却**漏了 `destination-in` 还原 alpha**，导致 `fillRect` 把整块（含透明像素）填成不透明实色。补上与原 `mul` 分支一致的 `destination-in` 步骤：`drawImage→multiply fillRect→destination-in drawImage→source-over`。两个着色分支(transparent 区)现均正确保留透明。
- **重构 `_getTintedTile colorize` 为逐像素灰度门控着色**（用户建议"取灰色度范围的像素来确定"）：从旧的三分类（纯灰遮罩/混合/全彩）改为**统一逐像素判断**：每个像素单独检查通道差 `cd=max(|R-G|,|G-B|,|R-B|)`；`cd<=24`(中性灰) → multiply 上色（保留纹理）；`cd>24`(彩色) → 保留原色；`alpha==0`(透明) → 跳过。天然消除纯色块问题（无需 destination-in），且不再需要三分类逻辑。验证：PIL 复现确认所有树 trunkErr=0.00、transAlphaΔ=0。
- **建造模式预览图上色**：`game.js _drawBuildIcon` 三类(cat=decor/wall/floor)均复用 renderer._getTintedTile 着色：decor 用 colorize 模式(和 drawDecoration 同缓存 key)，wall/floor 用 mul 模式(加 'icon_' 前缀避免与主绘制段裁剪坐标冲突)。game.js 新增 import tintForMat from material-tints.js。
- **修复 建造图标仍没上色**：上一轮编辑 `_drawBuildIcon` 时 old_string 未实际匹配（该方法体仍是旧版"直绘原图"），导致图标着色一直没生效。本轮回看确认后重写 `_drawBuildIcon` 接入着色，并补上 `_makeBuildItem` 调用漏传的 `it.id`（用于缓存 key）。用真实 Edge 进建造模式像素断言：oak(58) 图标 1238 像素全偏绿、birch(56) 80% 绿+20% 白干 → 证实着色生效。
- **`THRESH` 24→8（灰度范围收窄）**：实测 objs.png 通道差直方图，白桦(56)叶(cd<8)与干(cd 8~12)正好以 8 为断崖（[4,8)=13.4% / [8,12)=28.9%），THRESH=8 完美分隔→叶染色/干保留灰白(白桦白皮)；橡树 97.6% cd<8、樱/苹果彩色像素 cd>16 均不受影响。
